# ADR-0009: TTL и локальность кеша ResolveDistrict

**Статус:** Принято (Этап 12).
**Вопрос реестра:** Q12 (TTL), Q13 (локальность/технология кеша).
**Источник:** `docs/architecture/ecobilling-architecture.md`, раздел 21.8.

## Контекст

`ResolveDistrict` — критический быстрый путь (раздел 17.1), вызываемый на каждый запрос клиента. Нужно
было решить, кешировать ли результат резолва и если да, то с каким TTL и на какой технологии.

## Решение

- **Q12, TTL = 300 секунд.** Безопасная сеть на случай пропущенной явной инвалидации, а не основной
  механизм — основной механизм это явная инвалидация при `UpdateDistrict`/`Activate`/`DeactivateDistrict`.
- **Q13, in-memory**, через новую абстракцию `ICache` (`Application/Abstractions`) — `GetAsync`/`SetAsync`/
  `RemoveAsync`, спроектированную так, чтобы замена на распределённый кеш (Redis) не требовала изменения
  вызывающего кода.
- Кешируются только успешные (активные, найденные) резолвы — `district.not_found` и `district.inactive` не
  кешируются.
- **Не то же самое, что `expiresInSeconds` публичного контракта** (раздел 19.1, `3600` секунд) — два
  умышленно не связанных числа: одно означает «как долго клиент может доверять адресу без повторного
  resolve», другое — «как долго Control может отвечать из кеша, не читая PostgreSQL».

## Последствия

- При нескольких репликах каждая ведёт свой собственный in-memory кеш — не корректностная проблема
  (источник истины остаётся в PostgreSQL), но снижает эффективность кеша по мере роста числа реплик.
  Явно зафиксировано как известное ограничение, не блокирующее текущую эксплуатацию.
