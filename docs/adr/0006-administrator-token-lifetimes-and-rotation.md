# ADR-0006: Время жизни и ротация токенов администратора

**Статус:** Принято (Этап 6).
**Вопрос реестра:** Q5, Q6.
**Источник:** `docs/architecture/ecobilling-architecture.md`, раздел 21.4.

## Контекст

Нужно было зафиксировать конкретное время жизни access/refresh токенов системного администратора и способ
их хранения/ротации, без изобретения велосипеда с обнаружением кражи токена.

## Решение

- Access token живёт **15 минут**.
- Refresh token живёт **14 дней**, ротируется при каждом использовании (старый отзывается, новый выдаётся),
  хранится в базе только как **SHA-256 хеш** случайного значения — не PBKDF2: PBKDF2 намеренно медленный,
  чтобы противостоять подбору короткого пароля, а refresh token не подбираем (256 бит случайности), поэтому
  медленный хеш только тратит CPU впустую.
- **Обнаружение повторного использования:** если предъявленный refresh token уже был отозван предыдущей
  ротацией — признак кражи/replay. Реакция: отозвать **все** текущие активные refresh token этого
  администратора, требуя полного повторного входа везде.

## Последствия

- Обычная ротация (используемый токен ещё активен) не аудируется — рутинная операция при каждом вызове API,
  шум, а не сигнал безопасности.
- Обнаруженный replay аудируется отдельно, с `revokedSessionCount` в `AfterData` — единственный аудируемый
  путь refresh.
- Токены директора/контроллера/жителя — отдельный вопрос округа EcoBilling, не затронутый этим решением.
