# ADR-0005: Lockout входа администратора и rate limiting

**Статус:** Принято (Этап 10). Закрывает предупреждения "не готов к реальному/публичному трафику" на
`POST /api/v1/admin/auth/login` и `POST /api/v1/districts/resolve`, висевшие с Этапа 3/6.
**Источник:** `docs/architecture/ecobilling-architecture.md`, раздел 21.7.

## Контекст

Ни вход администратора, ни `ResolveDistrict` не имели защиты от подбора/перегрузки за пределами общей
рекомендации "код округа — не секрет, полагаться на rate limiting". Нужны были конкретные пороги.

## Решение

**Lockout по аккаунту (только вход администратора):**

- Порог: 5 подряд неудачных попыток на один аккаунт запускают lockout.
- Прогрессивная длительность, удваивается на каждом следующем lockout без успешного входа между ними,
  потолок 30 минут: 1 → 2 → 4 → 8 → 16 → 30.
- Счётчик и уровень эскалации сбрасываются при успешном входе; уровень эскалации отдельно сбрасывается
  после 24 часов без единой неудачной попытки (иначе легитимный пользователь после долгого перерыва
  получил бы уже максимальную эскалацию за одну случайную ошибку).
- Попытка во время активного lockout не продлевает/усиливает его; правильный пароль во время lockout тоже
  отклоняется.
- Наружу всегда один и тот же `administrator.invalid_credentials` — lockout не различим извне от обычного
  неверного пароля (та же нейтральность ошибки, что для неизвестного email).

**Rate limiting (`Microsoft.AspNetCore.RateLimiting`, без новых зависимостей), по IP:**

| Endpoint | Алгоритм | Лимит | Причина |
|---|---|---|---|
| `POST /api/v1/admin/auth/login` | Fixed window | 20/мин | Перехватывает распределённый подбор по многим email с одного источника — то, что lockout по аккаунту не может. |
| `POST /api/v1/districts/resolve` | Sliding window | 30/мин | Sliding, не fixed: fixed window допускает всплеск до 2x лимита на границе окна. |

## Последствия

- Партиционирование по `RemoteIpAddress` корректно только при прямом доступе из интернета; за reverse
  proxy/балансировщиком потребуется `ForwardedHeaders` — не решено здесь, зависит от ещё не определённой
  модели развёртывания.
- Отказы rate limiter'а не аудируются (высокообъёмны, не привязаны к аккаунту); lockout аудируется отдельным
  действием `administrator.locked_out`.
