## 1. Общая картина системы

EcoBilling состоит из двух независимых backend-систем. Они имеют отдельные решения, отдельные процессы развёртывания и отдельные PostgreSQL. Такое разделение изолирует данные округов и не превращает центральный сервис в узкое место для всех операций.

### 1.1 Что происходит при входе

- Пользователь вводит код округа в сайте или мобильном приложении.
- Клиент отправляет код в EcoBilling.Control.
- Control делает точечный поиск по уникальному индексу кода и возвращает доверенный адрес API округа.
- После этого клиент обращается напрямую к EcoBilling выбранного округа.
- Проверка логина, работа со счетами, показаниями и платежами выполняется только в базе округа.

### 1.2 Почему Control не проксирует весь трафик

- Падение Control после получения адреса не останавливает уже работающих пользователей округа.
- Нагрузка от миллионов жителей распределяется по backend-серверам округов.
- Персональные и финансовые данные не собираются в центральной базе.
- Каждый округ можно масштабировать, обслуживать и восстанавливать независимо.

### 1.3 Владение данными

| Данные | Владелец | Запрещённое дублирование |
|---|---|---|
| Код, название и API URL округа | EcoBilling.Control | Не копировать полный реестр во все базы округов. |
| Системные администраторы | EcoBilling.Control | Не создавать системного администратора в районном EcoBilling. |
| Директор, контроллеры и жители | EcoBilling округа | Control не хранит локальные учётные записи. |
| Лицевые счета, адреса, счётчики | EcoBilling округа | Не отправлять эти данные в Control. |
| Показания, тарифы, начисления, платежи | EcoBilling округа | Control не участвует в расчётах и оплате. |

## 2. Пользователи и права

Публичной самостоятельной регистрации нет. Все учётные записи создаются уполномоченным пользователем более высокого уровня.

| Роль | Где хранится | Как входит | Кто создаёт |
|---|---|---|---|
| Житель | EcoBilling округа | Лицевой счёт + пароль | Директор округа |
| Контроллер | EcoBilling округа | Email + пароль | Директор округа |
| Директор | EcoBilling округа | Email + пароль | Системный администратор через Control |
| Системный администратор | EcoBilling.Control | Email + пароль | Первичная установка / защищённая процедура |

### 2.1 Матрица возможностей

| Действие | Житель | Контроллер | Директор | Системный админ |
|---|---|---|---|---|
| Просмотр собственного счёта | Да | Нет | Да, в округе | Нет |
| Просмотр начислений и платежей | Только свои | По назначенным адресам | Весь округ | Нет |
| Ввод показаний | Нет | Да | Контроль | Нет |
| Оплата | Да | Нет | Просмотр | Нет |
| Создание жителя | Нет | Нет | Да | Нет |
| Создание контроллера | Нет | Нет | Да | Нет |
| Создание округа | Нет | Нет | Нет | Да |
| Создание первого директора | Нет | Нет | Нет | Да |

### 2.2 Ограничения жителя

- Может видеть только собственные данные, долг или переплату, начисления, историю показаний, оплаты и квитанции.
- Не изменяет профиль, адрес, лицевой счёт, показания или пароль самостоятельно.
- Сброс пароля выполняет директор. Политику безопасной передачи нового пароля ещё нужно определить.

### 2.3 Ограничения контроллера

- Работает только с назначенными жителями, адресами и маршрутами.
- Вводит новое показание, дату и служебное примечание, видит историю проверок.
- Не меняет тарифы, начисления, платежи и данные других округов.

### 2.4 Ограничения директора

- Управляет жителями, контроллерами, лицевыми счетами, адресами, счётчиками и назначениями своего округа.
- Видит показания, начисления, оплаты, долги и отчёты своего округа.
- Не создаёт округа, других директоров и системных администраторов.

# Часть I. EcoBilling — backend одного округа

## 4. Назначение и границы EcoBilling

Один развёрнутый экземпляр EcoBilling принадлежит одному округу. Он использует одну локальную PostgreSQL и обслуживает директора, контроллеров и жителей только этого округа.

**Входит в область EcoBilling**
- Аутентификация директора, контроллера и жителя.
- Профили жителей и сотрудников, адреса и лицевые счета.
- Счётчики, показания и история проверок.
- Тарифы, начисления, долги, переплаты и платежи.
- Отчёты округа, аудит и фоновые задания.
- Защищённый внутренний API для первоначального директора и сброса его пароля.

**Не входит в область EcoBilling**
- Глобальный реестр округов и разрешение кода округа.
- Системный администратор всей платформы.
- Чтение или изменение данных другого округа.

## 5. Проекты EcoBilling по отдельности

| Проект | Должен делать | Не должен делать |
|---|---|---|
| **EcoBilling.Api** | Принимает HTTP, валидирует транспортный ввод, вызывает сценарии модулей, формирует HTTP-ответ. | Бизнес-формулы, EF Core запросы, прямой доступ к таблицам. |
| **EcoBilling.Modules** | Содержит бизнес-сущности, правила, сценарии и контракты по модулям. | ASP.NET Core, контроллеры, PostgreSQL-драйверы, файловое хранилище. |
| **EcoBilling.Infrastructure** | Реализует PostgreSQL, аутентификацию, авторизацию, аудит, интеграции, outbox и наблюдаемость. | Входные HTTP endpoints и самостоятельные бизнес-решения. |
| **EcoBilling.Worker** | Запускает фоновые сценарии модулей по расписанию или очереди. | Дублирование формул начисления и прямое изменение таблиц в обход модулей. |
| **EcoBilling.SharedKernel** | Хранит минимальные технические типы: Result, Error, Pagination, Time, Idempotency. | Resident, Meter, Tariff, Payment и другие бизнес-сущности. |

### 5.1 EcoBilling.Api
- Endpoints группируются по функции, а внутренние межсервисные endpoints отделяются в `InternalEndpoints`.
- Middleware отвечает только за сквозные HTTP-задачи: обработку ошибок, correlation ID, журналирование запроса, аутентификацию.
- `Configuration` содержит типизированные настройки. `Extensions` содержит регистрацию сервисов и middleware.
- `Program.cs` является composition root: он соединяет интерфейсы Application/Modules с реализациями Infrastructure.

### 5.2 EcoBilling.Modules
Это центр бизнес-логики. Модуль не должен знать, откуда пришёл запрос — из HTTP, Worker или теста. Он получает команду или запрос и возвращает типизированный результат.

### 5.3 EcoBilling.Infrastructure
Infrastructure знает о модулях, потому что реализует объявленные ими интерфейсы. Обратная ссылка Modules → Infrastructure запрещена: иначе бизнес-правила становятся зависимыми от PostgreSQL и внешних сервисов.

### 5.4 EcoBilling.Worker
Worker не является вторым backend. Он только планирует и запускает существующие сценарии, передавая им идентификатор периода, задания или операции. Повторный запуск должен быть безопасным.

### 5.5 EcoBilling.SharedKernel
Новый тип добавляется в SharedKernel только если он действительно нужен нескольким модулям и не несёт предметного смысла конкретного модуля.

## 6. Бизнес-модули EcoBilling

| Модуль | Ответственность | Граница |
|---|---|---|
| **Identity** | Учётные записи, роли, вход, хеши паролей, токены и блокировки. | Не владеет счетами и платежами. |
| **Residents** | Профиль жителя, имя, адрес и связь с лицевыми счетами. | Не рассчитывает начисления. |
| **Controllers** | Профили контроллеров, назначения и доступные маршруты. | Не меняет тарифы и оплаты. |
| **Accounts** | Лицевой счёт, состояние, долг/переплата и связи с жителем. | Не хранит платёжные секреты. |
| **Meters** | Счётчики, серийные номера, установка, замена и статус. | Не принимает решения о тарифе. |
| **Readings** | Показания, дата, источник, контроллер и история исправлений. | Не перезаписывает историю без аудита. |
| **Tariffs** | Версии тарифов и периоды действия. | Не изменяет уже рассчитанные периоды без явного правила. |
| **Billing** | Расчёт начислений, перерасчёт и формирование обязательств. | Не определяет неподтверждённую формулу. |
| **Payments** | Регистрация оплаты, статусы, квитанции, возвраты и сверка. | Не считает оплату успешной до подтверждения провайдера. |
| **Reports** | Чтение агрегированных данных и формирование отчётов. | Не меняет операционные данные. |

### 6.1 Внутренняя структура модуля

```
Residents/
├── Domain/
│   ├── Entities/
│   ├── ValueObjects/
│   └── Rules/
├── Features/
│   ├── CreateResident/
│   ├── GetResident/
│   └── UpdateResident/
├── Contracts/
└── ResidentsModule.cs
```

- `Domain` содержит состояние и инварианты, но не HTTP и не EF Core.
- `Features` организует код по пользовательскому сценарию, а не по глобальным папкам Commands/Handlers для всего решения.
- `Contracts` содержит DTO или события, которые разрешено использовать снаружи модуля.
- Пустые папки и классы заранее не создаются. Срез появляется вместе с первым реальным сценарием и тестом.

## 7. Шаблон реализации одного сценария

Пример ниже показывает направление кода для `CreateResident`. Имена библиотек и конкретный mediator пока не фиксируются.

```
CreateResident/
├── CreateResidentCommand.cs     входные данные сценария
├── CreateResidentValidator.cs   структурная и бизнес-валидация
├── CreateResidentHandler.cs     оркестрация сценария
├── CreateResidentResult.cs      типизированный результат
└── CreateResidentEndpoint.cs    находится в Api, не в Modules
```

### Последовательность выполнения

| Шаг | Действие | Где выполняется |
|---|---|---|
| 1 | API проверяет формат JSON, аутентифицирует директора и получает correlation ID. | Api |
| 2 | Сценарий проверяет права директора и уникальность лицевого счёта. | Modules / Residents |
| 3 | Доменная модель создаёт жителя только при выполнении инвариантов. | Modules / Domain |
| 4 | Репозиторий сохраняет изменения в транзакции и добавляет outbox-событие при необходимости. | Infrastructure |
| 5 | API преобразует Result в 201, 400, 403 или 409 без утечки внутренних исключений. | Api |
| 6 | Unit, integration и endpoint-тесты подтверждают поведение. | tests |

> **Не смешивать слои.** Endpoint не должен строить SQL, Infrastructure не должна решать, можно ли создать жителя, а Worker не должен обходить сценарий CreateResident.

## 8. Аутентификация и управление аккаунтами EcoBilling

### 8.1 Подтверждённые правила

- Самостоятельной регистрации нет.
- Директор создаёт жителей и контроллеров своего округа.
- Житель входит по лицевому счёту и паролю.
- Контроллер и директор входят по email и паролю.
- Житель не меняет пароль самостоятельно; сброс выполняет директор.

### 8.2 Рекомендуемая техническая модель

- Единая таблица `Credentials` или `Users` для идентификатора входа, хеша пароля, роли и состояния; профили ролей хранятся отдельно.
- Пароль хранится только как адаптивный хеш с солью. Выбор алгоритма и параметров фиксируется отдельным решением безопасности.
- Access token короткоживущий; refresh token хранится и отзывается безопасно. Сроки жизни пока не утверждены.
- Каждый endpoint проверяет и роль, и принадлежность ресурса текущему округу/пользователю.
- Сброс пароля инвалидирует активные refresh tokens пользователя.

### 8.3 Состояния, которые нужно определить

| Вопрос | Почему важен | Статус |
|---|---|---|
| Политика сложности пароля | Влияет на создание и сброс всех аккаунтов. | НУЖНО РЕШИТЬ |
| Срок access/refresh token | Определяет баланс безопасности и удобства. | НУЖНО РЕШИТЬ |
| Блокировка после неудачных входов | Защищает от перебора паролей. | НУЖНО РЕШИТЬ |

## 11. Начисления, показания и платежи

### 11.1 Безопасный общий процесс начисления

| Этап | Что происходит | Что пока нельзя фиксировать |
|---|---|---|
| Закрытие периода | Определяется набор активных счетов и показаний на дату. | Точная дата и час закрытия. |
| Выбор тарифа | Берётся версия тарифа, действующая для периода. | Льготы и специальные категории. |
| Расчёт | Сценарий формирует начисление и объяснимые компоненты. | Формула, нормы, минимумы, округление. |
| Публикация | Начисление становится доступно жителю после успешной транзакции. | Правила ручного подтверждения. |
| Оплата | Создаётся попытка, затем принимается подтверждение провайдера. | Провайдер и способ распределения частичной оплаты. |
| Сверка | Worker повторно проверяет зависшие операции. | Периодичность и SLA провайдера. |

### 11.2 Идемпотентность

- Повторный запуск расчёта одного счёта за один период не создаёт второе начисление.
- Повторный callback платёжного провайдера не создаёт второй платёж.
- Worker может безопасно продолжить после аварийного завершения.
- Уникальные ограничения базы являются последней линией защиты от дублей.

> **НУЖНО РЕШИТЬ.** Формула расхода и начисления, тарифные периоды, округление, пени, льготы, перерасчёт, частичная оплата и возвраты. До решения этих вопросов модуль Billing нельзя считать спроектированным.

## 14. Развёртывание EcoBilling

Каждый округ разворачивает отдельный комплект: API, Worker и PostgreSQL. Docker Compose в репозитории предназначен прежде всего для локальной разработки; production-секреты и backup-политика настраиваются отдельно.

| Компонент | Масштабирование | Состояние |
|---|---|---|

# Часть II. EcoBilling.Control — центральный сервис

## 15. Назначение и границы Control

Control нужен не для счетов за воду, а для выбора правильного сервера округа и системного администрирования реестра округов.

**Входит в область Control**
- Разрешение кода округа в доверенный API URL.
- Аутентификация системного администратора.
- Создание и изменение округа.
- Создание первого директора и сброс его пароля через внутренний API округа.
- Аудит административных действий и состояние операций provisioning.

**Не входит в область Control**
- Жители, контроллеры, лицевые счета, показания, тарифы, начисления и платежи.
- Логин директора, контроллера или жителя.
- Прямое подключение к PostgreSQL округа.
- Проксирование всех пользовательских запросов после разрешения кода.

## 16. Проекты EcoBilling.Control по отдельности

| Проект | Ответственность | Ключевое ограничение |
|---|---|---|
| **Control.Api** | Публичный resolve endpoint, административные endpoints, middleware и DI. | Не содержит поиска через DbContext и правил создания округа. |
| **Control.Application** | ResolveDistrict, Create/UpdateDistrict, CreateDirector, ResetDirectorPassword, AdministratorLogin. | Зависит только от Domain; внешние системы представлены интерфейсами. |
| **Control.Domain** | District, Administrator, ProvisioningOperation, value objects и инварианты. | Не знает об ASP.NET Core, EF Core, HTTP и конфигурации. |
| **Control.Infrastructure** | PostgreSQL, миграции, токены, кеш, audit, outbox и DistrictClients. | Не принимает административные решения самостоятельно. |

### 16.1 Почему здесь нет Worker

На первом этапе отдельный Worker не нужен. Если появятся регулярные health-check округов, длительные retry provisioning или большие фоновые операции, Worker добавляется только после измеренной необходимости. До этого короткие операции выполняются API, а надёжность внешней команды обеспечивается outbox и контролируемым обработчиком.

### 16.2 Почему здесь нет SharedKernel

У Control всего три внутренних слоя. Общие типы можно держать в Domain/Application. Отдельный SharedKernel без реального повторного использования добавил бы лишнюю зависимость.

## 17. Сценарии Application в Control

| Сценарий | Вход | Результат / эффект |
|---|---|---|
| **ResolveDistrict** | Нормализованный код округа | Внутренний результат: активный DistrictId, Name и доверенный ApiBaseUrl. Наружу отдаётся только контракт 19.1. |
| **CreateDistrict** | Название, код, HTTPS API URL | Новый уникальный округ и запись аудита. |
| **UpdateDistrict** | DistrictId и разрешённые изменения | Обновлённый реестр, инвалидация кеша, аудит. |
| **CreateDirector** | DistrictId, имя, email и секрет первичной установки | Идемпотентная команда в API округа и статус provisioning. |
| **ResetDirectorPassword** | DistrictId, director identifier и данные сброса | Защищённая команда в округ, аудит результата. |
| **AdministratorLogin** | Email + пароль | Токены системного администратора или нейтральная ошибка. |

### 17.1 ResolveDistrict — критический быстрый путь

- Код нормализуется по одному утверждённому правилу до поиска.
- Поиск выполняется по уникальному индексу, а не сканированием таблицы.
- Неактивный или неизвестный округ возвращает одинаково безопасный контракт без внутренних деталей.
- Результат можно кешировать по нормализованному коду; обновление округа инвалидирует кеш.
- Control возвращает только заранее сохранённый и проверенный адрес, а не URL из пользовательского ввода.

### 17.2 CreateDirector — межсервисная операция

- Control не вставляет запись в базу округа напрямую.
- Control вызывает защищённый internal endpoint EcoBilling.
- Команда имеет operationId/idempotency key, чтобы retry не создал второго директора.
- Результат фиксируется в ProvisioningOperation и AuditLog.
- Открытый пароль не попадает в outbox, логи и диагностические события.

### 17.3 Формат и нормализация кода округа — ЗАФИКСИРОВАНО

Решение принято владельцем продукта и закрывает строку «Код округа» в реестре раздела 26.

| Свойство | Решение |
|---|---|
| Форма | Человекочитаемая, например `BISHKEK-01`. |
| Формат | 2–10 заглавных латинских букв, дефис, 2–4 цифры. |
| Регулярное выражение | `^[A-Z]{2,10}-[0-9]{2,4}$` (проверяется после нормализации). |
| Нормализация | `Trim()` + приведение к верхнему регистру по инвариантной культуре. |
| Чего нормализация НЕ делает | Не удаляет разделители, не выполняет NFKC, не меняет дефис. |
| Защита от перебора | Rate limiting на публичном endpoint, а не непрозрачность кода. |

- Приведение к верхнему регистру выполняется только инвариантной культурой. Культурно-зависимый `ToUpper()`
  запрещён: в тюркских локалях `i` переходит в `İ` и ломает поиск по уникальному индексу.
- Нормализация применяется одинаково при создании округа и при разрешении кода, иначе уникальный индекс
  и запрос resolve разойдутся.
- `NormalizedCode` — то, по чему построен уникальный индекс. `Code` хранит исходное написание для отображения.
- Класс цифр записан как `[0-9]`, а не `\d`. В .NET `\d` по умолчанию соответствует и не-ASCII
  десятичным цифрам (например арабо-индийским ٠١), из-за чего внешне другой код прошёл бы проверку.
- Формат сознательно перебираем. Это принятый компромисс: код округа — маршрутизатор, а не секрет
  (раздел 28, глоссарий). Единственная защита от перебора — ограничение частоты запросов.

**НУЖНО РЕШИТЬ:** можно ли менять код после активации округа. До решения код считается неизменяемым.

## 18. Предлагаемая модель данных Control

| Таблица | Ключевые поля | Правила |
|---|---|---|
| **Administrators** | Id, FullName, Email, NormalizedEmail, PasswordHash, IsActive, CreatedAt, UpdatedAt, LastLoginAt | `NormalizedEmail` уникален; пароль только как хеш; `PasswordHash` никогда не возвращается через API. |
| **Districts** | Id, Code, NormalizedCode, Name, ApiBaseUrl, Status, CreatedAt, UpdatedAt, ActivatedAt, DeactivatedAt | `NormalizedCode` уникален; `Status` — перечисление, не булево; URL проходит строгую валидацию. |
| **ProvisioningOperations** | Id, DistrictId, OperationType, IdempotencyKey, Status, RequestMetadata, ResultMetadata, AttemptCount, CreatedAt, StartedAt, CompletedAt, FailedAt, LastErrorCode | История создания директора/сброса без секретов. |
| **AuditLogs** | Id, AdministratorId, Action, EntityType, EntityId, BeforeData, AfterData, CorrelationId, IpAddress, UserAgent, CreatedAt | Неизменяемый журнал административных действий; секреты и `PasswordHash` исключены. |
| **OutboxMessages** | Id, Type, Payload, OccurredAt, ProcessedAt, RetryCount, LastError | Надёжная доставка допустимых команд/событий. |

**Состояние округа — ЗАФИКСИРОВАНО.** `Districts.Status` — перечисление `DistrictStatus`, а не флаг `IsActive`.
Булево поле не способно выразить требуемые отметки времени `ActivatedAt` / `DeactivatedAt` и историю переходов.
Переходы состояний определяются в `Domain/Districts` и покрываются unit-тестами, включая недопустимые переходы.

**Об учётной записи администратора.** `IsActive` — административное состояние: включён ли аккаунт вообще.
Это не то же самое, что временная блокировка после неудачных попыток входа.

**НУЖНО РЕШИТЬ:** как хранится состояние lockout администратора (счётчик неудачных попыток и время снятия
блокировки). Техническое задание требует аудита блокировки и восстановления доступа, но полей для этого
не задаёт. Не добавлять колонки до решения; связано со строкой «Пароли» в реестре раздела 26.

### 18.1 Индексы

- `Districts(NormalizedCode)` — UNIQUE; главный индекс resolve-запроса.
- `Administrators(NormalizedEmail)` — UNIQUE.
- `ProvisioningOperations(IdempotencyKey)` — UNIQUE; идемпотентность обеспечивается ограничением базы,
  а не только проверкой в памяти процесса.
- `ProvisioningOperations(Status, CreatedAt)` — для retry и мониторинга зависших операций.
- `AuditLogs(CreatedAt)` и `AuditLogs(EntityType, EntityId)` — для расследований.

> Исправлено в версии 0.2: прежняя редакция предписывала индекс `ProvisioningOperations(Status, UpdatedAt)`,
> хотя колонки `UpdatedAt` в этой таблице нет. Жизненный цикл операции описывают `CreatedAt`, `StartedAt`,
> `CompletedAt` и `FailedAt`, поэтому индекс построен по `CreatedAt`.

### 18.2 Что нельзя хранить

- Пароли директоров в открытом виде или обратимо зашифрованном виде без отдельной утверждённой модели.
- Лицевые счета, адреса жителей, показания, платежи и долги.
- Секреты сервисной аутентификации в обычных таблицах конфигурации или логах.

## 19. API EcoBilling.Control

### 19.1 Публичный endpoint разрешения

**Контракт по техническому заданию (раздел 9 ТЗ)**

```
POST /api/v1/districts/resolve
```

Request:
```json
{
  "districtCode": "BISHKEK-01"
}
```

Success 200:
```json
{
  "districtCode": "BISHKEK-01",
  "apiBaseUrl": "https://district-01.example.com",
  "expiresInSeconds": 3600
}
```

> Исправлено в версии 0.2: прежняя редакция использовала поле запроса `code` и возвращала
> `districtId` + `districtName` без `expiresInSeconds`. Авторитетным является техническое задание.
> `districtId` и `districtName` остаются во внутреннем результате сценария, но наружу не отдаются:
> клиенту для маршрутизации достаточно адреса, а лишние идентификаторы — это утечка деталей реестра.

- Ответ не содержит строку подключения, внутренние IP, состояние базы и административные данные.
- Endpoint защищается rate limit, нормализацией входа и ограничением длины.
- Код нормализуется и валидируется по правилу раздела 17.3 до обращения к базе.

**Коды ошибок публичного endpoint**

| Код | Когда |
|---|---|
| `district.invalid_code` | Код не проходит формат раздела 17.3. |
| `district.not_found` | Активный округ с таким кодом не найден. |
| `district.inactive` | Округ существует, но не активен. |
| `validation.failed` | Тело запроса не проходит валидацию. |
| `rate_limit.exceeded` | Превышен лимит частоты запросов. |

**`expiresInSeconds` — ЗАФИКСИРОВАНО.** Значение `3600` (час), как в примере технического задания,
принято как фиксированная константа публичного контракта.

> **Это не то же самое, что server-side кеш резолва Control (раздел 21.1, строка «Кеш TTL резолва» реестра раздела 26).**
> Два числа умышленно не связаны и не обязаны совпадать:
>
> | | `expiresInSeconds` | Server-side resolve-кеш (открытый вопрос) |
> |---|---|---|
> | Кто видит значение | Клиентское приложение. | Только Control; клиент не знает о нём. |
> | Что оно означает | «Как долго клиенту доверять этому адресу без повторного resolve». | «Как долго Control может отвечать из кеша, не читая PostgreSQL». |
> | Чем ограничено | Ничем технически — это контракт, который можно поменять в любой момент. | Задержкой инвалидации кеша при деактивации округа. |
> | Текущее значение | `3600`, зафиксировано здесь. | Не решено; открыто до Этапа 12. |
>
> Если два числа связать, будущий читатель может решить, что увеличение TTL внутреннего кеша автоматически
> меняет контракт с клиентом, или наоборот — что это одна настройка. Это не так: клиент имеет право
> продолжать использовать адрес весь час независимо от того, сколько раз Control успел обновить кеш за
> это время. Кеш TTL резолва остаётся отдельным открытым вопросом реестра раздела 26 до Этапа 12.

**НУЖНО РЕШИТЬ:** различать ли HTTP-статусом неизвестный и неактивный округ. Раздел 9 технического задания
требует не раскрывать, существует ли сервер технически. Рекомендация — отдавать один и тот же HTTP-статус
для `district.not_found` и `district.inactive`, различая их только кодом ошибки в теле.

## 20. Контракт Control → EcoBilling

Этот контракт — главная точка совместной работы двух разработчиков. Он должен быть версионирован, протестирован с обеих сторон и изменяться обратно совместимо.

**Предлагаемый вызов создания директора**

```
POST /internal/v1/directors

Headers:
  Authorization: <service credential>
  Idempotency-Key: <operation id>
  X-Correlation-Id: <trace id>

Body:
{
  "fullName": "...",
  "email": "director@example.com",
  "initialCredential": "..."
}

Response:
{
  "directorId": "...",
  "operationId": "...",
  "status": "created"
}
```

### 20.1 Обязательные свойства контракта

- Доступен только по защищённой внутренней сети или через проверенную service-to-service аутентификацию.
- Повтор с тем же Idempotency-Key возвращает тот же результат и не создаёт дубль.
- Email нормализуется одинаково; уникальность директора контролирует EcoBilling округа.
- Control не считает timeout доказательством неуспеха: он повторяет или запрашивает статус операции.
- Секрет первичной установки не записывается в обычный лог и исключается из телеметрии.

### 20.2 Общие коды межсервисных ошибок

| Код | Смысл | Поведение Control |
|---|---|---|
| `district.unavailable` | API округа недоступен. | Retry по политике; показать операцию как Pending/Failed. |
| `director.already_exists` | Директор или email уже существует. | Не повторять автоматически; показать конфликт. |
| `operation.already_processed` | Idempotency key уже обработан. | Принять сохранённый результат. |
| `service.unauthorized` | Service credential отклонён. | Не повторять бесконечно; критический alert. |
| `validation.failed` | Контрактные данные неверны. | Исправить запрос; не retry. |

## 21. Безопасность и производительность Control

### 21.1 Защита публичного resolve

- Уникальный индекс превращает поиск кода в точечную операцию, а не проверку миллионов пользователей.
- Кеш по коду уменьшает обращения к PostgreSQL; источник истины остаётся в базе.
- Rate limiting ограничивает перебор кодов и злоупотребление endpoint.
- Ответ может иметь короткий Cache-Control только после согласования поведения клиента и изменения адресов.

### 21.2 Защита административной части

- Административные endpoints отделены политикой SystemAdmin и не доступны по одному лишь district code.
- Каждое создание/изменение округа и provisioning директора записывается в аудит.
- ApiBaseUrl принимается только от администратора, требует HTTPS и проходит защиту от SSRF.
- Секреты сервисного доступа хранятся в secret store и регулярно ротируются.
- Ошибки не раскрывают наличие конкретного email системного администратора.

### 21.3 Поведение при сбоях

| Сбой | Ожидаемое поведение |
|---|---|
| Control DB недоступна | Resolve возвращает controlled 503; готовность instance становится false. |
| Кеш недоступен | Работа продолжается через PostgreSQL, если кеш не является обязательным. |
| API округа недоступен | Resolve может вернуть известный URL; provisioning переходит в retry/pending. |
| Control недоступен после resolve | Клиент продолжает работу напрямую с уже выбранным округом. |
| Timeout создания директора | Не делать вывод об успехе; повторять с тем же idempotency key. |

## 22. Тестирование и развёртывание Control

### 22.1 Тесты

- **Unit:** нормализация кода, уникальность, переходы ProvisioningOperation, правила активного округа.
- **Integration:** уникальные индексы PostgreSQL, миграции, кеш, outbox и fake district server.
- **Architecture:** Domain без ссылок; Application → Domain; Infrastructure → Application/Domain; Api → Application/Infrastructure.
- **E2E:** resolve активного/неизвестного округа, вход администратора, создание округа, retry создания директора.
- **Contract:** одна и та же версия примеров запросов запускается против Control client и EcoBilling internal API.

### 22.2 Развёртывание

- Control разворачивается отдельно от всех округов и имеет собственный домен/API endpoint.
- PostgreSQL Control не разделяется с базой какого-либо округа.
- API можно масштабировать горизонтально, если кеш и токены не зависят от памяти одной реплики.
- Изменение схемы Districts выполняется до публикации кода, который использует новые поля.
- Health endpoint проверяет процесс; readiness дополнительно проверяет PostgreSQL и обязательные зависимости.

- Неопределённые денежные правила вынесены в вопросы, а не в placeholder-формулы.

### 27.2 Перед началом функции Control

- Функция относится к коду округа, реестру или системному администрированию.
- Она не требует копирования данных жителей или платежей.
- Для внешнего вызова определены timeout, retry, idempotency и audit.
- ApiBaseUrl и другие адреса проходят allowlist/SSRF-защиту.
- Изменение контракта согласовано разработчиком EcoBilling.

### 27.3 Перед релизом

- Миграции проверены на чистой и существующей базе.
- Build/test проходят в Release-конфигурации.
- Секреты отсутствуют в репозитории, образах, логах и тестовых snapshots.
- Health/readiness и ключевые метрики доступны.
- Есть backup/rollback-план и проверен порядок совместного релиза двух сервисов.

## 28. Глоссарий

| Термин | Определение |
|---|---|
| Округ | Изолированная область эксплуатации с отдельным EcoBilling и PostgreSQL. |
| District code | Публичный маршрутизирующий код. Не является паролем или токеном. |
| Control | Центральный сервис реестра округов и системного администрирования. |
| Provisioning | Первоначальное создание директора или другая подготовка нового округа. |
| Vertical slice | Организация кода вокруг одного сценария от входа до результата. |
| Idempotency | Повтор одной операции не создаёт дополнительный эффект. |
| Outbox | Таблица сообщений, записываемая в одной транзакции с бизнес-данными для надёжной отправки. |
| Correlation ID | Идентификатор, связывающий логи и traces одного запроса между компонентами. |
| RPO | Максимально допустимая потеря данных по времени при аварии. |
| RTO | Максимально допустимое время восстановления сервиса. |
| ADR | Короткая запись архитектурного решения, причин и последствий. |

### Итог

Два проекта независимы по данным и развёртыванию, но связаны одним маленьким защищённым provisioning-контрактом. Главная защита архитектуры — не переносить бизнес-данные округа в Control и не переносить глобальное администрирование в районный EcoBilling.
