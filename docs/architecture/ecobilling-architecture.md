## 1. Общая картина системы

EcoBilling состоит из двух независимых backend-систем. Они имеют отдельные решения, отдельные процессы развёртывания и отдельные PostgreSQL. Такое разделение изолирует данные округов и не превращает центральный сервис в узкое место для всех операций.

### 1.1 Что происходит при входе

- Пользователь вводит код округа в сайте или мобильном приложении.
- Клиент отправляет код в EcoBilling.Control.
- Control делает точечный поиск по уникальному индексу кода и возвращает доверенный адрес API округа.
- После этого клиент обращается напрямую к EcoBilling выбранного округа.
- Проверка логина, работа со счетами, показаниями и платежами выполняется только в базе округа.

### 1.2 Почему Control не проксирует весь трафик

- Падение Control после получения адреса не останавливает уже работающих пользователей округа.
- Нагрузка от миллионов жителей распределяется по backend-серверам округов.
- Персональные и финансовые данные не собираются в центральной базе.
- Каждый округ можно масштабировать, обслуживать и восстанавливать независимо.

### 1.3 Владение данными

| Данные | Владелец | Запрещённое дублирование |
|---|---|---|
| Код, название и API URL округа | EcoBilling.Control | Не копировать полный реестр во все базы округов. |
| Системные администраторы | EcoBilling.Control | Не создавать системного администратора в районном EcoBilling. |
| Директор, контроллеры и жители | EcoBilling округа | Control не хранит локальные учётные записи. |
| Лицевые счета, адреса, счётчики | EcoBilling округа | Не отправлять эти данные в Control. |
| Показания, тарифы, начисления, платежи | EcoBilling округа | Control не участвует в расчётах и оплате. |

## 2. Пользователи и права

Публичной самостоятельной регистрации нет. Все учётные записи создаются уполномоченным пользователем более высокого уровня.

| Роль | Где хранится | Как входит | Кто создаёт |
|---|---|---|---|
| Житель | EcoBilling округа | Лицевой счёт + пароль | Директор округа |
| Контроллер | EcoBilling округа | Email + пароль | Директор округа |
| Директор | EcoBilling округа | Email + пароль | Системный администратор через Control |
| Системный администратор | EcoBilling.Control | Email + пароль | Первичная установка / защищённая процедура |

### 2.1 Матрица возможностей

| Действие | Житель | Контроллер | Директор | Системный админ |
|---|---|---|---|---|
| Просмотр собственного счёта | Да | Нет | Да, в округе | Нет |
| Просмотр начислений и платежей | Только свои | По назначенным адресам | Весь округ | Нет |
| Ввод показаний | Нет | Да | Контроль | Нет |
| Оплата | Да | Нет | Просмотр | Нет |
| Создание жителя | Нет | Нет | Да | Нет |
| Создание контроллера | Нет | Нет | Да | Нет |
| Создание округа | Нет | Нет | Нет | Да |
| Создание первого директора | Нет | Нет | Нет | Да |

### 2.2 Ограничения жителя

- Может видеть только собственные данные, долг или переплату, начисления, историю показаний, оплаты и квитанции.
- Не изменяет профиль, адрес, лицевой счёт, показания или пароль самостоятельно.
- Сброс пароля выполняет директор. Политику безопасной передачи нового пароля ещё нужно определить.

### 2.3 Ограничения контроллера

- Работает только с назначенными жителями, адресами и маршрутами.
- Вводит новое показание, дату и служебное примечание, видит историю проверок.
- Не меняет тарифы, начисления, платежи и данные других округов.

### 2.4 Ограничения директора

- Управляет жителями, контроллерами, лицевыми счетами, адресами, счётчиками и назначениями своего округа.
- Видит показания, начисления, оплаты, долги и отчёты своего округа.
- Не создаёт округа, других директоров и системных администраторов.

# Часть I. EcoBilling — backend одного округа

## 4. Назначение и границы EcoBilling

Один развёрнутый экземпляр EcoBilling принадлежит одному округу. Он использует одну локальную PostgreSQL и обслуживает директора, контроллеров и жителей только этого округа.

**Входит в область EcoBilling**
- Аутентификация директора, контроллера и жителя.
- Профили жителей и сотрудников, адреса и лицевые счета.
- Счётчики, показания и история проверок.
- Тарифы, начисления, долги, переплаты и платежи.
- Отчёты округа, аудит и фоновые задания.
- Защищённый внутренний API для первоначального директора и сброса его пароля.

**Не входит в область EcoBilling**
- Глобальный реестр округов и разрешение кода округа.
- Системный администратор всей платформы.
- Чтение или изменение данных другого округа.

## 5. Проекты EcoBilling по отдельности

| Проект | Должен делать | Не должен делать |
|---|---|---|
| **EcoBilling.Api** | Принимает HTTP, валидирует транспортный ввод, вызывает сценарии модулей, формирует HTTP-ответ. | Бизнес-формулы, EF Core запросы, прямой доступ к таблицам. |
| **EcoBilling.Modules** | Содержит бизнес-сущности, правила, сценарии и контракты по модулям. | ASP.NET Core, контроллеры, PostgreSQL-драйверы, файловое хранилище. |
| **EcoBilling.Infrastructure** | Реализует PostgreSQL, аутентификацию, авторизацию, аудит, интеграции, outbox и наблюдаемость. | Входные HTTP endpoints и самостоятельные бизнес-решения. |
| **EcoBilling.Worker** | Запускает фоновые сценарии модулей по расписанию или очереди. | Дублирование формул начисления и прямое изменение таблиц в обход модулей. |
| **EcoBilling.SharedKernel** | Хранит минимальные технические типы: Result, Error, Pagination, Time, Idempotency. | Resident, Meter, Tariff, Payment и другие бизнес-сущности. |

### 5.1 EcoBilling.Api
- Endpoints группируются по функции, а внутренние межсервисные endpoints отделяются в `InternalEndpoints`.
- Middleware отвечает только за сквозные HTTP-задачи: обработку ошибок, correlation ID, журналирование запроса, аутентификацию.
- `Configuration` содержит типизированные настройки. `Extensions` содержит регистрацию сервисов и middleware.
- `Program.cs` является composition root: он соединяет интерфейсы Application/Modules с реализациями Infrastructure.

### 5.2 EcoBilling.Modules
Это центр бизнес-логики. Модуль не должен знать, откуда пришёл запрос — из HTTP, Worker или теста. Он получает команду или запрос и возвращает типизированный результат.

### 5.3 EcoBilling.Infrastructure
Infrastructure знает о модулях, потому что реализует объявленные ими интерфейсы. Обратная ссылка Modules → Infrastructure запрещена: иначе бизнес-правила становятся зависимыми от PostgreSQL и внешних сервисов.

### 5.4 EcoBilling.Worker
Worker не является вторым backend. Он только планирует и запускает существующие сценарии, передавая им идентификатор периода, задания или операции. Повторный запуск должен быть безопасным.

### 5.5 EcoBilling.SharedKernel
Новый тип добавляется в SharedKernel только если он действительно нужен нескольким модулям и не несёт предметного смысла конкретного модуля.

## 6. Бизнес-модули EcoBilling

| Модуль | Ответственность | Граница |
|---|---|---|
| **Identity** | Учётные записи, роли, вход, хеши паролей, токены и блокировки. | Не владеет счетами и платежами. |
| **Residents** | Профиль жителя, имя, адрес и связь с лицевыми счетами. | Не рассчитывает начисления. |
| **Controllers** | Профили контроллеров, назначения и доступные маршруты. | Не меняет тарифы и оплаты. |
| **Accounts** | Лицевой счёт, состояние, долг/переплата и связи с жителем. | Не хранит платёжные секреты. |
| **Meters** | Счётчики, серийные номера, установка, замена и статус. | Не принимает решения о тарифе. |
| **Readings** | Показания, дата, источник, контроллер и история исправлений. | Не перезаписывает историю без аудита. |
| **Tariffs** | Версии тарифов и периоды действия. | Не изменяет уже рассчитанные периоды без явного правила. |
| **Billing** | Расчёт начислений, перерасчёт и формирование обязательств. | Не определяет неподтверждённую формулу. |
| **Payments** | Регистрация оплаты, статусы, квитанции, возвраты и сверка. | Не считает оплату успешной до подтверждения провайдера. |
| **Reports** | Чтение агрегированных данных и формирование отчётов. | Не меняет операционные данные. |

### 6.1 Внутренняя структура модуля

```
Residents/
├── Domain/
│   ├── Entities/
│   ├── ValueObjects/
│   └── Rules/
├── Features/
│   ├── CreateResident/
│   ├── GetResident/
│   └── UpdateResident/
├── Contracts/
└── ResidentsModule.cs
```

- `Domain` содержит состояние и инварианты, но не HTTP и не EF Core.
- `Features` организует код по пользовательскому сценарию, а не по глобальным папкам Commands/Handlers для всего решения.
- `Contracts` содержит DTO или события, которые разрешено использовать снаружи модуля.
- Пустые папки и классы заранее не создаются. Срез появляется вместе с первым реальным сценарием и тестом.

## 7. Шаблон реализации одного сценария

Пример ниже показывает направление кода для `CreateResident`. Имена библиотек и конкретный mediator пока не фиксируются.

```
CreateResident/
├── CreateResidentCommand.cs     входные данные сценария
├── CreateResidentValidator.cs   структурная и бизнес-валидация
├── CreateResidentHandler.cs     оркестрация сценария
├── CreateResidentResult.cs      типизированный результат
└── CreateResidentEndpoint.cs    находится в Api, не в Modules
```

### Последовательность выполнения

| Шаг | Действие | Где выполняется |
|---|---|---|
| 1 | API проверяет формат JSON, аутентифицирует директора и получает correlation ID. | Api |
| 2 | Сценарий проверяет права директора и уникальность лицевого счёта. | Modules / Residents |
| 3 | Доменная модель создаёт жителя только при выполнении инвариантов. | Modules / Domain |
| 4 | Репозиторий сохраняет изменения в транзакции и добавляет outbox-событие при необходимости. | Infrastructure |
| 5 | API преобразует Result в 201, 400, 403 или 409 без утечки внутренних исключений. | Api |
| 6 | Unit, integration и endpoint-тесты подтверждают поведение. | tests |

> **Не смешивать слои.** Endpoint не должен строить SQL, Infrastructure не должна решать, можно ли создать жителя, а Worker не должен обходить сценарий CreateResident.

## 8. Аутентификация и управление аккаунтами EcoBilling

### 8.1 Подтверждённые правила

- Самостоятельной регистрации нет.
- Директор создаёт жителей и контроллеров своего округа.
- Житель входит по лицевому счёту и паролю.
- Контроллер и директор входят по email и паролю.
- Житель не меняет пароль самостоятельно; сброс выполняет директор.

### 8.2 Рекомендуемая техническая модель

- Единая таблица `Credentials` или `Users` для идентификатора входа, хеша пароля, роли и состояния; профили ролей хранятся отдельно.
- Пароль хранится только как адаптивный хеш с солью. Выбор алгоритма и параметров фиксируется отдельным решением безопасности.
- Access token короткоживущий; refresh token хранится и отзывается безопасно. Сроки жизни пока не утверждены.
- Каждый endpoint проверяет и роль, и принадлежность ресурса текущему округу/пользователю.
- Сброс пароля инвалидирует активные refresh tokens пользователя.

### 8.3 Состояния, которые нужно определить

| Вопрос | Почему важен | Статус |
|---|---|---|

## 9. Предлагаемая модель данных EcoBilling

> **Важно.** Это проектная рекомендация, а не утверждённая схема. Поля и связи должны уточняться вместе с бизнес-правилами начислений и оплаты.

| Таблица | Ключевые данные | Ограничения / индексы |

### 9.1 Транзакционные границы

- Один пользовательский сценарий изменяет данные в одной локальной транзакции PostgreSQL.
- Внешний HTTP-вызов не удерживает открытую транзакцию базы.
- Событие, которое должно уйти наружу, записывается в Outbox той же транзакцией.
- Денежные значения используют decimal и явные правила округления после их утверждения.

## 11. Начисления, показания и платежи

### 11.1 Безопасный общий процесс начисления

| Этап | Что происходит | Что пока нельзя фиксировать |
|---|---|---|
| Закрытие периода | Определяется набор активных счетов и показаний на дату. | Точная дата и час закрытия. |
| Выбор тарифа | Берётся версия тарифа, действующая для периода. | Льготы и специальные категории. |
| Расчёт | Сценарий формирует начисление и объяснимые компоненты. | Формула, нормы, минимумы, округление. |
| Публикация | Начисление становится доступно жителю после успешной транзакции. | Правила ручного подтверждения. |
| Оплата | Создаётся попытка, затем принимается подтверждение провайдера. | Провайдер и способ распределения частичной оплаты. |
| Сверка | Worker повторно проверяет зависшие операции. | Периодичность и SLA провайдера. |

### 11.2 Идемпотентность

- Повторный запуск расчёта одного счёта за один период не создаёт второе начисление.
- Повторный callback платёжного провайдера не создаёт второй платёж.
- Worker может безопасно продолжить после аварийного завершения.
- Уникальные ограничения базы являются последней линией защиты от дублей.

> **НУЖНО РЕШИТЬ.** Формула расхода и начисления, тарифные периоды, округление, пени, льготы, перерасчёт, частичная оплата и возвраты. До решения этих вопросов модуль Billing нельзя считать спроектированным.

## 14. Развёртывание EcoBilling

Каждый округ разворачивает отдельный комплект: API, Worker и PostgreSQL. Docker Compose в репозитории предназначен прежде всего для локальной разработки; production-секреты и backup-политика настраиваются отдельно.

| Компонент | Масштабирование | Состояние |
|---|---|---|
| API | Несколько реплик за load balancer при необходимости. | Stateless; токены и файлы не должны жить только в памяти процесса. |

- Версия API, версия миграции и commit SHA доступны в диагностике.

# Часть II. EcoBilling.Control — центральный сервис

## 15. Назначение и границы Control

Control нужен не для счетов за воду, а для выбора правильного сервера округа и системного администрирования реестра округов.

**Входит в область Control**
- Разрешение кода округа в доверенный API URL.
- Аутентификация системного администратора.
- Создание и изменение округа.
- Создание первого директора и сброс его пароля через внутренний API округа.
- Аудит административных действий и состояние операций provisioning.

**Не входит в область Control**
- Жители, контроллеры, лицевые счета, показания, тарифы, начисления и платежи.
- Логин директора, контроллера или жителя.
- Прямое подключение к PostgreSQL округа.
- Проксирование всех пользовательских запросов после разрешения кода.

## 16. Проекты EcoBilling.Control по отдельности

| Проект | Ответственность | Ключевое ограничение |
|---|---|---|
| **Control.Api** | Публичный resolve endpoint, административные endpoints, middleware и DI. | Не содержит поиска через DbContext и правил создания округа. |
| **Control.Application** | ResolveDistrict, Create/UpdateDistrict, CreateDirector, ResetDirectorPassword, AdministratorLogin. | Зависит только от Domain; внешние системы представлены интерфейсами. |
| **Control.Domain** | District, Administrator, ProvisioningOperation, value objects и инварианты. | Не знает об ASP.NET Core, EF Core, HTTP и конфигурации. |
| **Control.Infrastructure** | PostgreSQL, миграции, токены, кеш, audit, outbox и DistrictClients. | Не принимает административные решения самостоятельно. |

### 16.1 Почему здесь нет Worker

На первом этапе отдельный Worker не нужен. Если появятся регулярные health-check округов, длительные retry provisioning или большие фоновые операции, Worker добавляется только после измеренной необходимости.

**Уточнено на Этапе 8.** CreateDirector/ResetDirectorPassword вызывают EcoBilling синхронно в рамках того же
HTTP-запроса администратора, с ограниченным набором попыток (раздел 21.6), а не через Outbox и отдельный фоновый
обработчик, как предполагала более ранняя редакция этого раздела. Если попытки исчерпаны, `ProvisioningOperation`
помечается `Failed`, и администратор видит отказ немедленно; повторная попытка запускается явным повторным вызовом
того же административного endpoint, который переиспользует существующую операцию и её `Idempotency-Key`
(раздел 9.2), а не автоматическим фоновым retry. Outbox остаётся нереализованным (раздел 18) -- он был бы нужен
для модели "принять запрос немедленно, обработать позже", которую Control сознательно не выбрал для этого сценария:
провижининг директора -- редкая, осознанная административная операция, где немедленная обратная связь важнее, чем
не блокировать HTTP-ответ на время вызова округа.

### 16.2 Почему здесь нет SharedKernel

У Control всего три внутренних слоя. Общие типы можно держать в Domain/Application. Отдельный SharedKernel без реального повторного использования добавил бы лишнюю зависимость.

## 17. Сценарии Application в Control

| Сценарий | Вход | Результат / эффект |
|---|---|---|
| **ResolveDistrict** | Нормализованный код округа | Внутренний результат: активный DistrictId, Name и доверенный ApiBaseUrl. Наружу отдаётся только контракт 19.1. |
| **CreateDistrict** | Название, код, HTTPS API URL | Новый уникальный округ и запись аудита. |
| **UpdateDistrict** | DistrictId и разрешённые изменения | Обновлённый реестр, инвалидация кеша, аудит. |
| **CreateDirector** | DistrictId, имя, email и секрет первичной установки | Идемпотентная команда в API округа и статус provisioning. |
| **ResetDirectorPassword** | DistrictId, director identifier и данные сброса | Защищённая команда в округ, аудит результата. |
| **AdministratorLogin** | Email + пароль | Токены системного администратора или нейтральная ошибка. |

### 17.1 ResolveDistrict — критический быстрый путь

- Код нормализуется по одному утверждённому правилу до поиска.
- Поиск выполняется по уникальному индексу, а не сканированием таблицы.
- Неактивный или неизвестный округ возвращает одинаково безопасный контракт без внутренних деталей.
- Результат можно кешировать по нормализованному коду; обновление округа инвалидирует кеш.
- Control возвращает только заранее сохранённый и проверенный адрес, а не URL из пользовательского ввода.

### 17.2 CreateDirector — межсервисная операция -- РЕАЛИЗОВАНО (Этап 8)

- Control не вставляет запись в базу округа напрямую.
- Control вызывает защищённый internal endpoint EcoBilling (раздел 20.1).
- Команда имеет idempotency key, чтобы retry не создал второго директора (раздел 20.3).
- Результат фиксируется в `ProvisioningOperation` и `AuditEntries` (раздел 18, раздел 21.5).
- **Уточнено на Этапе 8** (раздел 9.4, раздел 20.1): Control не просто не логирует пароль -- он вообще не участвует
  в его передаче. Ни команда `CreateDirector`, ни вызов `IDistrictClient.CreateDirectorAsync` не содержат поля для
  пароля в принципе, а не просто маскируют его в логах. Пароль директора целиком генерируется и доставляется
  EcoBilling-ом.

### 17.3 Формат и нормализация кода округа — ЗАФИКСИРОВАНО

Решение принято владельцем продукта и закрывает строку «Код округа» в реестре раздела 26.

| Свойство | Решение |
|---|---|
| Форма | Человекочитаемая, например `BISHKEK-01`. |
| Формат | 2–10 заглавных латинских букв, дефис, 2–4 цифры. |
| Регулярное выражение | `^[A-Z]{2,10}-[0-9]{2,4}$` (проверяется после нормализации). |
| Нормализация | `Trim()` + приведение к верхнему регистру по инвариантной культуре. |
| Чего нормализация НЕ делает | Не удаляет разделители, не выполняет NFKC, не меняет дефис. |
| Защита от перебора | Rate limiting на публичном endpoint, а не непрозрачность кода. |

- Приведение к верхнему регистру выполняется только инвариантной культурой. Культурно-зависимый `ToUpper()`
  запрещён: в тюркских локалях `i` переходит в `İ` и ломает поиск по уникальному индексу.
- Нормализация применяется одинаково при создании округа и при разрешении кода, иначе уникальный индекс
  и запрос resolve разойдутся.
- `NormalizedCode` — то, по чему построен уникальный индекс. `Code` хранит исходное написание для отображения.
- Класс цифр записан как `[0-9]`, а не `\d`. В .NET `\d` по умолчанию соответствует и не-ASCII
  десятичным цифрам (например арабо-индийским ٠١), из-за чего внешне другой код прошёл бы проверку.
- Формат сознательно перебираем. Это принятый компромисс: код округа — маршрутизатор, а не секрет
  (раздел 28, глоссарий). Единственная защита от перебора — ограничение частоты запросов.

**НУЖНО РЕШИТЬ:** можно ли менять код после активации округа. До решения код считается неизменяемым.

| **ProvisioningOperations** — РЕАЛИЗОВАНО (Этап 8) | Id, DistrictId, OperationType, IdempotencyKey, Status, AttemptCount, CreatedAt, StartedAt, CompletedAt, FailedAt, LastErrorCode | История создания директора/сброса без секретов. **Без `RequestMetadata`/`ResultMetadata`**, в отличие от первоначального проекта этой строки: то, что было бы в них (email, `directorId`), уже попадает в `AuditEntries.AfterData` при успехе (раздел 21.5) -- отдельное поле дублировало бы его без дополнительной пользы, пока не появится собственная причина читать эти детали не через аудит. |
| **AuditEntries** — РЕАЛИЗОВАНО (Этап 7) | Id, AdministratorId (nullable, без FK), Action, EntityType, EntityId, BeforeData (jsonb), AfterData (jsonb), CorrelationId, IpAddress, UserAgent, CreatedAt | Неизменяемый журнал административных действий; секреты и `PasswordHash` исключены. Названа `AuditEntries`, а не `AuditLogs` из первоначального проекта раздела 18 -- название выровнено с фактическим кодом (`IAuditRepository`, `IAuditWriter`). `AdministratorId` сознательно без внешнего ключа: неизвестный email при входе и создание администратора через Provisioning CLI аудируются без существующего/ещё не существующего администратора (раздел 21.5). |
| **OutboxMessages** | Id, Type, Payload, OccurredAt, ProcessedAt, RetryCount, LastError | Надёжная доставка допустимых команд/событий. Пока не реализовано. |

**Состояние округа — ЗАФИКСИРОВАНО.** `Districts.Status` — перечисление `DistrictStatus`, а не флаг `IsActive`.
Булево поле не способно выразить требуемые отметки времени `ActivatedAt` / `DeactivatedAt` и историю переходов.
Переходы состояний определяются в `Domain/Districts` и покрываются unit-тестами, включая недопустимые переходы.

**Об учётной записи администратора.** `IsActive` — административное состояние: включён ли аккаунт вообще.
Это не то же самое, что временная блокировка после неудачных попыток входа.

**НУЖНО РЕШИТЬ:** как хранится состояние lockout администратора (счётчик неудачных попыток и время снятия
блокировки). Техническое задание требует аудита блокировки и восстановления доступа, но полей для этого
не задаёт. Не добавлять колонки до решения; связано со строкой «Пароли» в реестре раздела 26.

### 18.1 Индексы

- `Districts(NormalizedCode)` — UNIQUE; главный индекс resolve-запроса.
- `Administrators(NormalizedEmail)` — UNIQUE.
- `ProvisioningOperations(IdempotencyKey)` — UNIQUE; идемпотентность обеспечивается ограничением базы,
  а не только проверкой в памяти процесса.
- `ProvisioningOperations(DistrictId)` — UNIQUE, **частичный** (`WHERE "OperationType" = 'DirectorCreation'`),
  добавлено на Этапе 9. Гарантирует "не более одной операции создания директора на округ" на уровне базы --
  собственная проверка обработчика (`GetLatestAsync` перед вставкой) не может быть атомарной сама по себе, и
  без этого индекса два одновременных запроса `CreateDirector` для одного округа могли бы оба пройти проверку
  до того, как хотя бы один из них зафиксируется (раздел 21.6). Индекс частичный, а не на всю таблицу: сброс
  пароля (`PasswordReset`) осознанно повторяем (раздел 9.2) и не подпадает под это ограничение.
- `ProvisioningOperations(Status, CreatedAt)` — для retry и мониторинга зависших операций.
- `AuditEntries(CreatedAt)`, `AuditEntries(EntityType, EntityId)` и `AuditEntries(AdministratorId)` —
  для расследований (**реализовано, Этап 7**; третий индекс добавлен сверх первоначального
  проекта раздела 18, так как просмотр действий одного администратора -- отдельный частый запрос).

> Исправлено в версии 0.2: прежняя редакция предписывала индекс `ProvisioningOperations(Status, UpdatedAt)`,
> хотя колонки `UpdatedAt` в этой таблице нет. Жизненный цикл операции описывают `CreatedAt`, `StartedAt`,
> `CompletedAt` и `FailedAt`, поэтому индекс построен по `CreatedAt`.

### 18.2 Что нельзя хранить

- Пароли директоров в открытом виде или обратимо зашифрованном виде без отдельной утверждённой модели.
- Лицевые счета, адреса жителей, показания, платежи и долги.
- Секреты сервисной аутентификации в обычных таблицах конфигурации или логах.

## 19. API EcoBilling.Control

### 19.1 Публичный endpoint разрешения

**Контракт по техническому заданию (раздел 9 ТЗ)**

```
POST /api/v1/districts/resolve
```

Request:
```json
{
  "districtCode": "BISHKEK-01"
}
```

Success 200:
```json
{
  "districtCode": "BISHKEK-01",
  "apiBaseUrl": "https://district-01.example.com",
  "expiresInSeconds": 3600
}
```

> Исправлено в версии 0.2: прежняя редакция использовала поле запроса `code` и возвращала
> `districtId` + `districtName` без `expiresInSeconds`. Авторитетным является техническое задание.
> `districtId` и `districtName` остаются во внутреннем результате сценария, но наружу не отдаются:
> клиенту для маршрутизации достаточно адреса, а лишние идентификаторы — это утечка деталей реестра.

- Ответ не содержит строку подключения, внутренние IP, состояние базы и административные данные.
- Endpoint защищается rate limit (**реализовано, Этап 10** -- раздел 21.7), нормализацией входа и ограничением длины.
- Код нормализуется и валидируется по правилу раздела 17.3 до обращения к базе.

**Коды ошибок публичного endpoint**

| Код | Когда |
|---|---|
| `district.invalid_code` | Код не проходит формат раздела 17.3. |
| `district.not_found` | Активный округ с таким кодом не найден. |
| `district.inactive` | Округ существует, но не активен. |
| `validation.failed` | Тело запроса не проходит валидацию. |
| `rate_limit.exceeded` | Превышен лимит частоты запросов. |

**`expiresInSeconds` — ЗАФИКСИРОВАНО.** Значение `3600` (час), как в примере технического задания,
принято как фиксированная константа публичного контракта.

> **Это не то же самое, что server-side кеш резолва Control (раздел 21.1, строка «Кеш TTL резолва» реестра раздела 26).**
> Два числа умышленно не связаны и не обязаны совпадать:
>
> | | `expiresInSeconds` | Server-side resolve-кеш (открытый вопрос) |
> |---|---|---|
> | Кто видит значение | Клиентское приложение. | Только Control; клиент не знает о нём. |
> | Что оно означает | «Как долго клиенту доверять этому адресу без повторного resolve». | «Как долго Control может отвечать из кеша, не читая PostgreSQL». |
> | Чем ограничено | Ничем технически — это контракт, который можно поменять в любой момент. | Задержкой инвалидации кеша при деактивации округа. |
> | Текущее значение | `3600`, зафиксировано здесь. | Не решено; открыто до Этапа 12. |
>
> Если два числа связать, будущий читатель может решить, что увеличение TTL внутреннего кеша автоматически
> меняет контракт с клиентом, или наоборот — что это одна настройка. Это не так: клиент имеет право
> продолжать использовать адрес весь час независимо от того, сколько раз Control успел обновить кеш за
> это время. Кеш TTL резолва остаётся отдельным открытым вопросом реестра раздела 26 до Этапа 12.

**НУЖНО РЕШИТЬ:** различать ли HTTP-статусом неизвестный и неактивный округ. Раздел 9 технического задания
требует не раскрывать, существует ли сервер технически. Рекомендация — отдавать один и тот же HTTP-статус
для `district.not_found` и `district.inactive`, различая их только кодом ошибки в теле.

## 20. Контракт Control → EcoBilling — ЗАФИКСИРОВАНО (Этап 8)

Этот контракт — главная точка совместной работы двух разработчиков. Он должен быть версионирован, протестирован с обеих сторон и изменяться обратно совместимо. Версия ниже описывает то, что Control сейчас реально реализует и вызывает
(`Infrastructure/DistrictClients/DistrictClient.cs`) -- это готовая спецификация для команды EcoBilling, а не черновик; разделы 20.1-20.5 нужно реализовать на стороне EcoBilling именно так, как здесь описано, чтобы два сервиса заработали
вместе без дополнительного согласования.

> **Что изменилось по сравнению с прежней редакцией.** Прежний набросок передавал `initialCredential` в теле запроса
> и не описывал ResetDirectorPassword вовсе. Оба вопроса были явными открытыми пунктами реестра раздела 26 и решены
> на Этапе 8 (раздел 9.4/9.5 обсуждения этапа): **EcoBilling полностью владеет генерацией учётных данных директора** --
> и первого пароля при создании, и нового пароля при сбросе. Control никогда не получает, не хранит и не передаёт
> пароль директора в любом виде, ни в одном из двух вызовов. Способ, которым EcoBilling передаёт директору его новый
> пароль (email, принудительная смена при первом входе и т.д.), остаётся открытым вопросом EcoBilling (раздел 8.3),
> но он полностью на стороне EcoBilling -- Control в этом не участвует и не должен участвовать.

### 20.1 CreateDirector

```
POST /internal/v1/directors

Headers:
  Authorization: Bearer <service assertion JWT -- раздел 20.4>
  Idempotency-Key: <ключ идемпотентности операции>
  X-Correlation-Id: <trace id>
  Content-Type: application/json

Body:
{
  "fullName": "Full Name",
  "email": "director@district.example.com"
}
```

Ответ при успехе (директор создан только сейчас) -- `201 Created`:

```json
{
  "directorId": "...",
  "operationId": "...",
  "status": "created"
}
```

Ответ при повторе с тем же `Idempotency-Key`, который EcoBilling уже обработал ранее (раздел 20.3) -- `200 OK`,
**то же самое тело**, что и при первом успехе:

```json
{
  "directorId": "...",
  "operationId": "...",
  "status": "created"
}
```

- Пароль директора здесь никогда не передаётся ни в одном направлении (раздел 9.4). EcoBilling сам генерирует
  начальный пароль или иной способ первого входа и сам решает, как сообщить его директору.
- `directorId` -- идентификатор, которым владеет EcoBilling; Control хранит его только как непрозрачную строку
  в `ProvisioningOperations.ResultMetadata`-подобном поле, не интерпретируя и не проверяя формат.
- `operationId` в теле ответа -- идентификатор EcoBilling для этого же вызова на его стороне, для его собственной
  диагностики. Это отдельное значение от `ProvisioningOperationId`, которым Control именует свою запись того же
  вызова (раздел 18) -- у каждой стороны своя история операции, связанная только вызовом, а не общим первичным
  ключом.

### 20.2 ResetDirectorPassword

```
POST /internal/v1/directors/reset-password

Headers:
  Authorization: Bearer <service assertion JWT -- раздел 20.4>
  Idempotency-Key: <ключ идемпотентности операции>
  X-Correlation-Id: <trace id>
  Content-Type: application/json

Body:
{
  "email": "director@district.example.com"
}
```

Ответ при успехе (сброс запущен/выполнен) -- `202 Accepted`:

```json
{
  "operationId": "...",
  "status": "in_progress"
}
```

- Идентифицирует директора по email, а не по `directorId`: Control не хранит директорские идентификаторы как
  собственные данные (раздел 1.3), поэтому у административного вызова нет способа передать что-то более точное.
- Как и в CreateDirector, новый пароль здесь не передаётся ни в одном направлении (раздел 9.5). EcoBilling сам
  генерирует новый пароль и сам решает, как сообщить его директору.
- В отличие от CreateDirector, повторный вызов с новым `Idempotency-Key` для того же email -- это не ошибка и не
  повтор: сброс пароля осознанно повторяемая операция (Этап 8, раздел 9.2). `director.already_exists` для этого
  вызова не имеет смысла и никогда не возвращается; вместо него при неизвестном email возвращается
  `director.not_found`.

### 20.3 Идемпотентность

- `Idempotency-Key` идентифицирует одну логическую попытку операции на стороне Control, не одно HTTP-соединение:
  при таймауте или сетевом сбое Control повторяет вызов с **тем же самым** ключом, а не генерирует новый (Этап 8,
  раздел 9.2).
- EcoBilling обязан хранить, какой результат соответствует каждому обработанному `Idempotency-Key` (по крайней мере
  для CreateDirector, где повтор должен быть неотличим от первого успеха, кроме HTTP-статуса). Повторный вызов с уже
  обработанным ключом должен вернуть **тот же** `directorId` и тело ответа, что и первый успешный вызов, со статусом
  `200 OK` вместо `201 Created` -- Control не различает эти два случая иначе, чем по статус-коду, и не имеет
  отдельного кода ошибки `operation.already_processed`: это не ошибка, а принятый успешный результат.
- Ключ уникален в рамках EcoBilling-инстанса одного округа; коллизии между округами невозможны и не должны
  проверяться -- у каждого округа свой `Idempotency-Key`-namespace.

### 20.4 Аутентификация вызова -- ЗАФИКСИРОВАНО (Этап 8, раздел 9.1)

Каждый вызов Control несёт подписанный JWT ("service assertion") в заголовке `Authorization: Bearer <token>`.
Асимметричная подпись (ES256), не общий секрет: EcoBilling никогда не получает ничего, что само по себе позволяло
бы выдавать себя за Control.

**Формат токена**

| Claim | Значение | Проверка на стороне EcoBilling |
|---|---|---|
| `iss` | `"ecobilling-control"` | Должен точно совпадать. |
| `aud` | `NormalizedCode` округа-адресата (раздел 17.3) | Должен точно совпадать с кодом СВОЕГО округа -- токен, выпущенный для другого округа, отклоняется. Это защита от повторного использования токена не по адресу. |
| `sub` | `"ecobilling-control"` | Информационный; не обязателен для бизнес-логики. |
| `jti` | Случайное значение, уникальное на каждый вызов | Не обязателен для проверки; EcoBilling МОЖЕТ дополнительно отслеживать недавно увиденные значения для более строгой защиты от повторного воспроизведения в пределах короткого срока жизни токена, но не обязан. |
| `exp` / `iat` / `nbf` | Срок жизни не более 2 минут от момента выпуска | Обязательная проверка срока действия. Такой короткий срок жизни -- осознанное решение (см. ниже, "отзыв"). |

**Алгоритм подписи:** ES256 (ECDSA с кривой P-256, SHA-256). EcoBilling проверяет подпись открытым ключом Control
(ниже) через стандартную библиотеку JWT-валидации своей платформы -- это не требует собственного криптографического
кода, только конфигурация обычного JWT bearer middleware с открытым ключом вместо общего секрета.

**Распространение ключа.** Control хранит один приватный подписывающий ключ (`ServiceAuth:Jwt:SigningKeyPem`,
никогда не публикуется). Соответствующий открытый ключ передаётся команде EcoBilling отдельно, вне этого документа
(защищённый канал, не Git), и настраивается в конфигурации каждого округа-инстанса EcoBilling один раз. **Живого
JWKS-эндпоинта (`/.well-known/jwks.json`) пока нет** -- это осознанно отложенное решение (Этап 8, раздел 9.1):
при небольшом числе округов ручное распространение значения открытого ключа проще, чем протокол автоматического
обновления. Это первый кандидат на доработку, если число округов вырастет настолько, что ручная раздача станет
обременительной -- в этом случае распространение ключа станет самообслуживаемым без изменения самого формата
токена.

**Ротация.** Если приватный ключ Control меняется: (1) генерируется новая пара ключей; (2) новое значение открытого
ключа раздаётся команде EcoBilling и настраивается на стороне каждого округа; (3) после подтверждения, что все
округа обновили конфигурацию, Control переключается на подпись новым ключом. Требует координации между командами
на время перехода -- это принятая стоимость отсутствия JWKS (см. выше).

**Отзыв.** Специального механизма отзыва (denylist, revocation list) не существует и не нужен: срок жизни токена
не более 2 минут, поэтому скомпрометированный ключ прекращает быть опасным практически сразу после того, как
Control перестаёт подписывать им новые токены -- нет долгоживущего токена, который нужно было бы отдельно
аннулировать.

### 20.5 Коды ошибок

Ошибка возвращается как JSON-тело `{"code": "...", "message": "..."}` с соответствующим HTTP-статусом. Control
не читает `message` программно -- только `code`; `message` предназначен для логов/диагностики EcoBilling и не
интерпретируется Control-ом.

| Код | HTTP-статус | Когда | Поведение Control |
|---|---|---|---|
| `validation.failed` | `400` | Тело запроса не проходит валидацию (например, `email` не является email). | Возвращает клиенту как есть; не повторяет. |
| `service.unauthorized` | `401` или `403` | Service assertion (раздел 20.4) отсутствует, истёк, подписан не тем ключом или `aud` не совпадает с этим округом. | Не повторяет автоматически; это инфраструктурная проблема (например, ключи разошлись), а не временный сбой. |
| `director.already_exists` | `409` | CreateDirector с **новым** `Idempotency-Key` для округа, где директор уже существует (не путать с повтором того же ключа -- раздел 20.3, это не ошибка). | Не повторяет; сообщает конфликт администратору. |
| `director.not_found` | `404` | ResetDirectorPassword: email не соответствует ни одному директору этого округа. | Не повторяет; сообщает администратору. |
| *(любой другой код, включая отсутствие ответа, таймаут, 5xx)* | любой | Что угодно ещё -- сетевой сбой, таймаут, необработанное исключение EcoBilling. | Всё это Control сворачивает в собственный внутренний `district.unavailable` и повторяет по политике раздела 21 (10 секунд на попытку, 3 попытки, экспоненциальная задержка), а не считает таймаут доказательством неуспеха. |

- `district.unavailable` -- это код, который видит **администратор Control**, а не код, который отправляет
  EcoBilling: он не входит в контракт HTTP-ответа выше, это то, во что Control превращает любой нераспознанный
  сбой связи.
- Приведённая таблица -- полный набор кодов, которые EcoBilling должен уметь возвращать (кроме `district.unavailable`,
  который является внутренней интерпретацией Control, а не кодом ответа EcoBilling). Новый код, не входящий в этот
  список, будет интерпретирован Control как непризнанный сбой (`district.unavailable`) -- если EcoBilling нужен
  дополнительный код ошибки, это отдельное изменение контракта, согласованное заранее (раздел 23.2), а не
  одностороннее добавление.

## 21. Безопасность и производительность Control

### 21.1 Защита публичного resolve

- Уникальный индекс превращает поиск кода в точечную операцию, а не проверку миллионов пользователей.
- Кеш по коду уменьшает обращения к PostgreSQL; источник истины остаётся в базе.
- Rate limiting ограничивает перебор кодов и злоупотребление endpoint.
- Ответ может иметь короткий Cache-Control только после согласования поведения клиента и изменения адресов.

### 21.2 Защита административной части

- Административные endpoints отделены политикой SystemAdmin и не доступны по одному лишь district code.
- Каждое создание/изменение округа и provisioning директора записывается в аудит.
- ApiBaseUrl принимается только от администратора, требует HTTPS и проходит защиту от SSRF.
- Секреты сервисного доступа хранятся в secret store и регулярно ротируются.
- Ошибки не раскрывают наличие конкретного email системного администратора.

**Список разрешённых хостов округа — ЗАФИКСИРОВАНО (Этап 5).** Помимо структурных проверок
`TrustedApiUrl` (раздел 17.3: HTTPS, без userinfo, без query/fragment, без loopback/private/
link-local/metadata-адресов -- Этап 1), `CreateDistrict` и `UpdateDistrict` дополнительно
проверяют хост нового `ApiBaseUrl` по явному списку в конфигурации (`Districts:AllowedHosts`).
Оба уровня защиты действуют одновременно, второй не заменяет первый.

- Формат -- явный список точных хостов, а не маска домена. Модель развёртывания округов
  (единый домен под управлением Control или размещение округом самостоятельно) пока не
  определена; явный список -- более безопасный выбор на время, пока это не решено.
- Формат конфигурации спроектирован как *append-only*: поле называется `AllowedHosts`, а
  не, например, `AllowedExactHosts`, чтобы возможное будущее ослабление до маски доменов
  (`AllowedHostSuffixes`) можно было добавить отдельным полем, не переименовывая и не
  перестраивая существующее.
- Пустой или отсутствующий список означает «ничего не разрешено», а не «проверка отключена».
- Проверка применяется только к новому/изменяемому адресу от администратора, а не при каждом
  чтении округа из базы: `TrustedApiUrl.Create` используется и при перечитывании уже
  сохранённой строки, и повторная проверка по текущему списку на каждом чтении означала бы,
  что сокращение списка задним числом ломает уже существующие округа.

### 21.3 Поведение при сбоях

| Сбой | Ожидаемое поведение |
|---|---|
| Control DB недоступна | Resolve возвращает controlled 503; готовность instance становится false. |
| Кеш недоступен | Работа продолжается через PostgreSQL, если кеш не является обязательным. |
| API округа недоступен | Resolve может вернуть известный URL; provisioning переходит в retry/pending. |
| Control недоступен после resolve | Клиент продолжает работу напрямую с уже выбранным округом. |
| Timeout создания директора | Не делать вывод об успехе; повторять с тем же idempotency key. |

### 21.4 Аутентификация системного администратора -- ЗАФИКСИРОВАНО (Этап 6)

- **Q11 (хеширование).** PBKDF2 через встроенный `PasswordHasher<TUser>` ASP.NET Core
  Identity. Не Argon2id -- без новых зависимостей; современные параметры итераций
  PBKDF2 соответствуют текущим рекомендациям NIST для системы с небольшим числом
  администраторов.
- **Q10 (политика паролей).** Базовый уровень NIST SP 800-63B: минимум 12 символов, без
  принудительной сложности, без принудительной периодической смены. Проверка по списку
  утечек (например HaveIBeenPwned) сознательно не реализована в этом этапе -- внешняя
  сетевая зависимость, отложена как будущее улучшение.
- **Q5/Q6 (токены).** Access token живёт 15 минут. Refresh token живёт 14 дней,
  ротируется при каждом использовании (старый отзывается, новый выдаётся), хранится в
  базе только как SHA-256 хеш случайного значения -- не PBKDF2: PBKDF2 намеренно
  медленный, чтобы противостоять подбору короткого пароля, а refresh token не подбираем
  (256 бит случайности), поэтому медленный хеш не нужен и тратит CPU впустую.
- **Обнаружение повторного использования.** Если предъявленный refresh token уже был
  отозван предыдущей ротацией, это признак кражи/replay -- отзываются все текущие
  активные refresh token этого администратора, требуя полного повторного входа везде.
- **Q4 (создание первого администратора).** Отдельная консольная команда provisioning
  (`EcoBilling.Control.Provisioning`), а не seed при старте веб-процесса на основе
  секрета из окружения. Единственный способ создать администратора вообще -- нет ни
  публичной регистрации, ни HTTP endpoint для этого. Пароль запрашивается интерактивно
  с маскированным вводом, никогда не передаётся как аргумент командной строки.
- **Нейтральность ошибки входа.** `administrator.invalid_credentials` не различает
  неизвестный email, неверный пароль, неактивный аккаунт и lockout (Этап 10) -- строже,
  чем ResolveDistrict (раздел 19.1), поскольку этот раздел требует не раскрывать
  существование конкретного email, а администраторов немного, что делает вход
  реалистичной целью подбора. Внутри сценарий отдельно различает `administrator.inactive`
  и `administrator.locked_out` для аудита (Этап 7, Этап 10), но наружу это никогда не
  отдаётся -- даже правильный пароль во время активного lockout получает тот же самый
  `administrator.invalid_credentials` (раздел 21.7).

**РЕШЕНО (Этап 10):** политика lockout и rate limiting на обоих ранее открытых
endpoint'ах (вход администратора и ResolveDistrict) -- раздел 21.7. Оба предупреждения
о неготовности к реальному/публичному трафику (это и раздел 19.1) снимаются этим
решением.

### 21.5 Политика аудита административных действий -- ЗАФИКСИРОВАНО (Этап 7)

`AuditEntry` (раздел 18) пишется через `IAuditWriter` в Application-обработчиках; сама запись
только *подготавливается* (`Write` — синхронный, ничего не сохраняет), а физическую фиксацию
выполняет тот же `IUnitOfWork.SaveChangesAsync()`, которым обработчик сохраняет бизнес-изменение —
поэтому аудит и бизнес-изменение всегда попадают в PostgreSQL одной транзакцией: либо оба, либо
ни одного (проверено интеграционным тестом с принудительным нарушением уникального индекса).
`IHttpContextAccessor` подключён в Infrastructure (`AuditWriter`), а не в Application: он
обогащает запись `CorrelationId`/`IpAddress`/`UserAgent` из актуального HTTP-запроса
непосредственно перед сохранением, и Application ни разу не видит эти поля -- обработчики
передают в `AuditEntry` для этих трёх полей `null`, значения выставляются позже. Это единственный
способ, которым у обоих сценариев Provisioning CLI (нет HTTP-запроса вовсе) и обычного HTTP
endpoint работает один и тот же `AuditWriter`.

Что аудируется и с каким `AdministratorId`:

| Событие | Аудируется? | `AdministratorId` | Причина |
|---|---|---|---|
| CreateDistrict — успех и **каждый** отказ (invalid_code, invalid_url, invalid_name, code_conflict, host_not_allowed) | Да | Вызывающий администратор | Административное изменение реестра округов; отказ так же важен для расследования, как и успех. |
| UpdateDistrict — успех и каждый отказ | Да | Вызывающий администратор | Аналогично; снимок "before" делается сразу после загрузки, до попытки мутации, чтобы частично изменённое состояние не испортило запись при последующем отказе валидации. |
| Activate/DeactivateDistrict — успех, идемпотентный повтор (округ уже в этом статусе) и отказ | Да, включая повтор | Вызывающий администратор | Идемпотентный повтор — это реальное решение администратора подтвердить состояние, а не шум; Before и After в записи совпадают, что сигнализирует "ничего не изменилось". |
| AdministratorLogin — вход с неизвестным email | Да | `null` (аккаунта нет) | `AfterData` содержит `attemptedEmail` (не секрет) -- виден паттерн попыток входа под несуществующие адреса. |
| AdministratorLogin — неверный пароль известного аккаунта | Да | Известный `AdministratorId` | Внешний код ошибки не отличается от неизвестного email (раздел 21.4), но внутренняя запись аудита отличает эти два случая. |
| AdministratorLogin — неактивный аккаунт | Да | Известный `AdministratorId` | `AfterData` содержит внутренний код `administrator.inactive`, отдельно от `invalid_credentials`. |
| AdministratorLogin — успех | Да | Известный `AdministratorId` | Обычный успешный вход. |
| RefreshAdministratorSession — обычная ротация (используемый токен ещё активен) | **Нет** | -- | Осознанное решение владельца продукта: рутинная ротация происходит при каждом вызове API и не несёт сигнала -- это шум, а не событие безопасности. |
| RefreshAdministratorSession — обнаружено повторное использование уже отозванного токена | Да | Известный `AdministratorId` | Признак кражи/replay; `AfterData` содержит `revokedSessionCount`. Единственный аудируемый путь refresh. |
| AdministratorLogout | **Нет** | -- | Осознанное решение владельца продукта: рутинная операция, не событие безопасности и не бизнес-событие. |
| CreateAdministrator (через Provisioning CLI) — успех | Да | `null` (нет вызывающего HTTP-администратора — операция запускается локально с секретом окружения) | `EntityId` = Id нового администратора. |
| CreateAdministrator (через Provisioning CLI) — отказ | Да | `null` | `AfterData` содержит `attemptedEmail` и код ошибки. |
| ListDistricts, GetDistrict, ListAuditEntries | **Нет** | -- | Read-only запросы не изменяют состояние; аудит самого чтения журнала аудита создал бы бесконечную рекурсию сигнала. |
| CreateDirector — успех и каждый отказ (включая `director.already_exists`, отклонённый до вызова EcoBilling) | Да (**Этап 8**) | Вызывающий администратор | `EntityType="ProvisioningOperation"`; `AfterData` никогда не содержит пароль директора (раздел 20.1/9.4) -- команда сама его не носит. |
| ResetDirectorPassword — успех и каждый отказ | Да (**Этап 8**) | Вызывающий администратор | Симметрично CreateDirector; то же самое исключение пароля (раздел 20.2/9.5). |
| GetProvisioningOperation | **Нет** | -- | Read-only, та же причина, что у остальных read-only запросов выше. |

Все решения этой таблицы приняты владельцем продукта явно, построчно, 25 сентября 2026 года --
не выведены разработчиком по умолчанию.

### 21.6 Отказоустойчивость вызовов округа -- ЗАФИКСИРОВАНО (Этап 8, раздел 9.3)

`DistrictClient` (раздел 20) вызывает EcoBilling синхронно с ограниченным набором попыток: **10 секунд на попытку,
3 попытки всего, экспоненциальная задержка с джиттером между попытками**. Таймаут применяется к каждой попытке
отдельно, а не ко всей операции в целом -- третья попытка получает такой же полный десятисекундный бюджет, как и
первая, а не то, что осталось от общего окна. Реализовано через `Microsoft.Extensions.Http.Resilience`
(`ServiceCollectionExtensions.AddDistrictClient`), а не собственноручно написанным циклом повторов.

Если все 3 попытки исчерпаны, вызывающий обработчик (CreateDirector/ResetDirectorPassword) видит это как обычный
отказ `district.unavailable` и помечает `ProvisioningOperation` как `Failed` -- дальнейшие повторы не автоматические,
а требуют нового вызова того же административного endpoint (раздел 16.1, раздел 9.2).

**Дополнено на Этапе 9: гонка между конкурентными запросами.** Собственная проверка `CreateDirectorHandler`
("уже существует операция создания директора для этого округа?") -- это чтение в одном `DbContext`, а вставка новой
операции не фиксируется до финального `SaveChangesAsync` в конце обработчика, после сетевого вызова длительностью
до ~30 секунд (три попытки выше). Если два запроса для одного округа приходят почти одновременно, оба могут пройти
проверку до того, как хотя бы один зафиксируется -- частичный уникальный индекс `ProvisioningOperations(DistrictId)`
(раздел 18.1) существует именно для того, чтобы поймать это на уровне базы, а не полагаться на то, что проверка
в памяти процесса атомарна (она не атомарна).

**`IUnitOfWork.SaveChangesAsync` сам по себе не изменился.** Его контракт и поведение остаются точно такими же,
как до Этапа 9 -- он и дальше пробрасывает `DbUpdateException` как есть, для любого обработчика, кроме
CreateDirector. Вместо изменения общего метода на интерфейс добавлен один новый, узко специализированный метод:

```csharp
public interface IUnitOfWork
{
    Task SaveChangesAsync(CancellationToken cancellationToken); // не изменился

    Task<Result> SaveChangesOrConflictAsync(CancellationToken cancellationToken); // новый, Этап 9
}
```

`EfUnitOfWork.SaveChangesOrConflictAsync` перехватывает именно нарушение именно этого индекса (по `SqlState`
Postgres, не по тексту сообщения) и возвращает `Result.Failure(UnitOfWorkErrors.ConcurrencyConflict)` --
`UnitOfWorkErrors` -- статический класс в `Application.Abstractions` (не в `Domain.Common`: это технический сигнал
уровня хранения, который интерпретирует Application, а не понятие бизнес-инварианта уровня Domain). `Result`, а не
исключение: начиная с Этапа 2 в этой кодовой базе ожидаемые, обрабатываемые исходы -- это значения (`Result`), не
исключения, и гонка с конкретным, предусмотренным исходом вписывается в этот же принцип лучше, чем
throw/catch. `CreateDirectorHandler` проверяет `IsFailure` и возвращает `provisioning.concurrent_conflict`
(раздел 19.2) вместо необработанного исключения; проигравший запрос просто повторяется администратором и корректно
переиспользует уже зафиксированную операцию через `GetLatestAsync`.

Это узко специализированное решение, а не общее правило: `SaveChangesOrConflictAsync` существует специально для
этой конкретной, предусмотренной гонки CreateDirector и пока больше нигде не используется. Ни один другой
обработчик не обязан использовать этот метод, и `IUnitOfWork.SaveChangesAsync` для них не меняется ни в поведении,
ни в контракте -- расширять этот подход на другие сценарии стоит только тогда, когда для них найдётся такая же
конкретная, предусмотренная гонка, как здесь, а не как системное правило "все commit должны быть conflict-aware".

### 21.7 Lockout входа администратора и rate limiting -- ЗАФИКСИРОВАНО (Этап 10)

Снимает оба предупреждения "не готов к реальному/публичному трафику" -- с `POST /api/v1/admin/auth/login`
(раздел 21.4) и с `POST /api/v1/districts/resolve` (раздел 19.1) -- висевшие с Этапа 3/6.

**Lockout по аккаунту (только вход администратора).**

- Порог: 5 подряд неудачных попыток входа на один аккаунт запускают lockout.
- Прогрессивная длительность, удваивается на каждом следующем lockout без успешного входа между ними,
  с потолком 30 минут: 1 → 2 → 4 → 8 → 16 → 30 (и далее остаётся 30).
- Счётчик неудачных попыток и уровень эскалации сбрасываются на успешном входе.
- Уровень эскалации также сбрасывается к первому уровню, если прошло 24 часа без единой неудачной попытки --
  иначе злоумышленник мог бы "накопить" максимальную эскалацию против администратора, который просто давно
  не заходил, и первая же случайная неудачная попытка легитимного пользователя получила бы 30-минутный lockout.
- Новые поля `Administrator`: `LockedUntil` (nullable timestamp), `FailedLoginAttempts` (int),
  `ConsecutiveLockouts` (int), `LastFailedLoginAt` (nullable timestamp, необходим для 24-часового сброса --
  не входил в первоначальный список полей этого решения, добавлен как техническое следствие того же правила).
  Тот же паттерн "guard-before-mutate", что и везде в Domain (`District.Activate`, `ProvisioningOperation`).
  Закрывает строку «Пароли» реестра раздела 26, отдельно от `IsActive`: lockout -- временное,
  самовосстанавливающееся состояние безопасности, а не административный переключатель.
- Попытка входа во время активного lockout -- **не** увеличивает счётчик и не продлевает/усиливает lockout
  (иначе злоумышленник мог бы бесконечно продлевать чужой lockout, просто продолжая долбить endpoint).
  Правильный пароль во время активного lockout тоже отклоняется -- lockout, который правильный пароль мог бы
  обойти, не был бы lockout'ом.
- Новое действие аудита: `administrator.locked_out`, отдельно от `administrator.login_failed`. Аудируется
  только попытка, которая **запускает** lockout (её не сопровождает отдельная запись `login_failed` -- это
  избыточный шум для одного события); каждая последующая попытка во время уже активного lockout аудируется
  как обычный `administrator.login_failed`, с `errorCode: "administrator.locked_out"` в `AfterData`.
- Нейтральность ошибки (раздел 21.4) распространяется и на lockout: наружу всегда `administrator.invalid_credentials`,
  свёртка происходит в `AdministratorAuthEndpoints` (тот же механизм, что уже сворачивал `administrator.inactive` --
  Этап 6/7), а не в обработчике и не в `ApiError`.

**Rate limiting (`Microsoft.AspNetCore.RateLimiting`, без новых зависимостей), по IP, две отдельные политики.**

| Endpoint | Алгоритм | Лимит | Причина алгоритма |
|---|---|---|---|
| `POST /api/v1/admin/auth/login` | Fixed window | 20 запросов/минуту | Вторичный слой поверх lockout по аккаунту -- перехватывает распределённый подбор по многим email с одного источника, который lockout (привязанный к одному аккаунту) не может перехватить. |
| `POST /api/v1/districts/resolve` | Sliding window | 30 запросов/минуту | У ResolveDistrict нет понятия аккаунта, только IP. Sliding, а не fixed: fixed window допускает всплеск до 2x лимита на границе окна (N запросов в конце одной минуты + N в начале следующей); sliding устраняет это по конструкции. |

- Партиционирование по `HttpContext.Connection.RemoteIpAddress`. Корректно только при прямом доступе из
  интернета: если Control окажется за reverse proxy или балансировщиком, все запросы будут выглядеть так, как
  будто пришли с адреса самого proxy, если отдельно не настроить и не доверить `ForwardedHeaders` middleware.
  Не решено здесь -- сама модель развёртывания ещё не определена (раздел 3.1).
- Отказ -- `429`, тот же конверт ошибки (`ApiErrorResponse`), что и весь остальной API, код
  `rate_limit.exceeded` (раздел 19.1), с заголовком `Retry-After`, когда он вычислим. Формируется прямо в
  `OnRejected` -- это отказ на уровне middleware, до вызова любого endpoint-обработчика, поэтому `ApiError.ToResult`
  здесь не используется.
- Отказы rate limiter'а **не аудируются** -- высокообъёмны и не привязаны к конкретному аккаунту, тот же
  принцип, что уже применялся к обычной ротации refresh token (раздел 21.5): это шум, не сигнал.

## 22. Тестирование и развёртывание Control

### 22.1 Тесты

- **Unit:** нормализация кода, уникальность, переходы ProvisioningOperation, правила активного округа.
- **Integration:** уникальные индексы PostgreSQL, миграции, кеш, outbox и fake district server.
- **Architecture:** Domain без ссылок; Application → Domain; Infrastructure → Application/Domain; Api → Application/Infrastructure.
- **E2E:** resolve активного/неизвестного округа, вход администратора, создание округа, retry создания директора.
- **Contract:** одна и та же версия примеров запросов запускается против Control client и EcoBilling internal API.

### 22.2 Развёртывание

- Control разворачивается отдельно от всех округов и имеет собственный домен/API endpoint.
- PostgreSQL Control не разделяется с базой какого-либо округа.
- API можно масштабировать горизонтально, если кеш и токены не зависят от памяти одной реплики.
- Изменение схемы Districts выполняется до публикации кода, который использует новые поля.
- Health endpoint проверяет процесс; readiness дополнительно проверяет PostgreSQL и обязательные зависимости.

## 27. Чек-листы разработчиков

### 27.1 Перед началом функции EcoBilling

- Определён модуль-владелец и пользовательская роль.
- Известны вход, успешный результат и бизнес-ошибки.
- Подтверждено, какие таблицы изменяются одной транзакцией.
- Решено, нужен ли outbox и idempotency key.
- Неопределённые денежные правила вынесены в вопросы, а не в placeholder-формулы.

### 27.2 Перед началом функции Control

- Функция относится к коду округа, реестру или системному администрированию.
- Она не требует копирования данных жителей или платежей.
- Для внешнего вызова определены timeout, retry, idempotency и audit.
- ApiBaseUrl и другие адреса проходят allowlist/SSRF-защиту.
- Изменение контракта согласовано разработчиком EcoBilling.

### 27.3 Перед релизом

- Миграции проверены на чистой и существующей базе.
- Build/test проходят в Release-конфигурации.
- Секреты отсутствуют в репозитории, образах, логах и тестовых snapshots.
- Health/readiness и ключевые метрики доступны.
- Есть backup/rollback-план и проверен порядок совместного релиза двух сервисов.

## 28. Глоссарий

| Термин | Определение |
|---|---|
| Округ | Изолированная область эксплуатации с отдельным EcoBilling и PostgreSQL. |
| District code | Публичный маршрутизирующий код. Не является паролем или токеном. |
| Control | Центральный сервис реестра округов и системного администрирования. |
| Provisioning | Первоначальное создание директора или другая подготовка нового округа. |
| Vertical slice | Организация кода вокруг одного сценария от входа до результата. |
| Idempotency | Повтор одной операции не создаёт дополнительный эффект. |
| Outbox | Таблица сообщений, записываемая в одной транзакции с бизнес-данными для надёжной отправки. |
| Correlation ID | Идентификатор, связывающий логи и traces одного запроса между компонентами. |
| RPO | Максимально допустимая потеря данных по времени при аварии. |
| RTO | Максимально допустимое время восстановления сервиса. |
| ADR | Короткая запись архитектурного решения, причин и последствий. |

### Итог

Два проекта независимы по данным и развёртыванию, но связаны одним маленьким защищённым provisioning-контрактом. Главная защита архитектуры — не переносить бизнес-данные округа в Control и не переносить глобальное администрирование в районный EcoBilling.
